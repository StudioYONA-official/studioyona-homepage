## Goal

- 4개 앱 상세 페이지를 기능 나열 수준에서 벗어나, 앱이 어떤 문제를 푸는지와 실제로 어떻게 동작하는지 이해할 수 있는 랜딩페이지로 확장한다.

## Scope

- 포함: 앱 도입부 서술, 4단계 사용 흐름, 사용 사례, 상세 사양 표, 주요 기능 목록 구체화, 관련 CSS.
- 제외: 법무 문서, 홈·apps 페이지 구조 변경, 신규 스크린샷 추가, 배포.

## Findings

- 기존 상세 페이지의 주요 기능 목록은 대부분 추상적이었다. 예를 들어 EDSN Frame은 `다양한 색상, 그라디언트, 캐릭터 프레임으로 사진을 꾸며 보세요` 수준이라 실제 컷 수나 특수 프레임 종류를 알 수 없었다.
- 각 앱 프로젝트에 이미 사실 근거가 있었다. EDSN Frame은 `docs/APP_STORE_CONNECT_METADATA_DRAFT_2026-04-28.md`, 탐정의 녹음기는 `RecorderFix/docs/APP_STORE_METADATA_DRAFT_KO_2026-05-24.md`, 까꿍캠은 `Peekaboo_cam/docs/APP_SPEC.md`, Veruma는 `Previewcam/docs/VERUMA_IMPLEMENTATION_PLAN.md`와 `README.md`가 각각 authority다.
- 까꿍캠 `APP_SPEC.md`에서 음성 프리셋 5개 제한, 시각 큐 1~5단계, 촬영 직전·타이머 마지막 1초 부스트, 저장물 미합성 원칙을 확인했다.
- Veruma는 제품 명제가 `Capture the preview, not the camera's interpretation of the preview`로 문서에 명시되어 있어, 이를 도입부의 중심 메시지로 사용했다.

## Decisions

- 결정: 앱마다 `도입부 + 4단계 흐름 → 주요 기능 → 앱 정보 → 사용 사례 → 상세 사양` 순서로 통일한다.
  이유: 방문자가 `이게 뭔지 → 어떻게 쓰는지 → 나에게 맞는지 → 정확한 조건` 순으로 읽게 되고, 4개 앱 사이의 비교도 쉬워지기 때문이다.
- 결정: 사용 사례는 앱마다 4개로 고정하고 추상적 대상 대신 구체적 상황으로 쓴다.
  이유: `가족과 개인 모두에게` 같은 서술은 아무 정보도 주지 못하는 반면, `강의와 수업`처럼 상황을 지정하면 방문자가 자기 경우를 대입할 수 있다.
- 결정: 상세 사양은 카드 목록이 아니라 라벨/값 2열 행으로 표현한다.
  이유: 항목이 8~10개로 많고 값이 길어 카드로 만들면 스캔이 어렵다. 좁은 화면에서는 1열로 떨어지도록 처리했다.
- 결정: 새 색이나 새 폰트를 도입하지 않고 기존 카드·토큰 언어를 그대로 쓴다.
  이유: `docs/design.md`의 절제된 에디토리얼 톤을 유지하고, 페이지 사이 이질감을 만들지 않기 위해서다.

## Addendum 2026-07-29: 밴드 기반 랜딩 레이아웃으로 재작성

### 문제

- 1차 확장은 내용을 채웠지만 모두 같은 `card panel` 안에 담겨, 페이지 전체가 균일한 밀도의 카드 20여 개로 보였다. 위계가 없어 어디를 먼저 봐야 할지 알기 어려웠다.
- 스크린샷이 본문 맨 아래 부록처럼 놓였고 `loading="lazy"` 때문에 첫 화면에서는 빈 상자로 보였다.
- `docs/design.md`가 규정한 `warm sand ↔ deep dark rhythm`과 이미지 중심 구성이 상세 페이지에는 전혀 적용되어 있지 않았다.

### 결정

- 결정: `card panel` 나열 대신 전체 폭 밴드를 교차시킨다. 밝은 샌드 밴드와 딥다크 밴드가 번갈아 나오며 한 밴드에 한 가지 이야기만 담는다.
  이유: `design.md`의 핵심 리듬이고, 색이 바뀌는 지점이 곧 주제가 바뀌는 지점이 되어 스크롤만으로 구조가 읽힌다.
- 결정: 스크린샷을 전용 다크 밴드로 올리고 `loading="lazy"`를 제거한다. 그림자를 넣어 기기 화면처럼 띄운다.
  이유: 앱 상세 페이지에서 화면 이미지는 부록이 아니라 핵심 근거다.
- 결정: 사용 흐름은 카드가 아니라 번호 + 제목 + 설명의 3열 행으로 표현한다.
  이유: 순서가 있는 내용이므로 병렬 카드보다 목록 형태가 정확하고, 카드 테두리가 사라져 밀도가 낮아진다.
- 결정: 주요 기능은 큰 스크린샷과 나란히 두는 2단 `split`으로 만든다.
  이유: 텍스트만 이어지는 구간을 끊고, 설명과 실제 화면을 같은 시야에서 대조할 수 있다.
- 결정: 히어로 직후 밴드에 큰 서체의 단일 주장과 지표 3개를 둔다.
  이유: 방문자가 처음 만나는 화면에서 앱의 존재 이유가 한 문장으로 전달되어야 한다.

### 검증

- `python3 -m html.parser` 8개 페이지 통과, `git diff --check` 통과, 로컬 HTTP 200 8건.
- Playwright 전체 페이지 캡처로 데스크톱 1280px에서 밴드 교차와 쇼케이스 3열을, 모바일 390px에서 밴드 적층과 쇼케이스 1열 전환을 확인했다.
- 다크 밴드에서 `cases` 상단선, 제목, `secondary` 버튼, `spec-rows` 구분선의 대비가 부족해 다크 전용 규칙을 추가로 정의했다.

## Addendum 2026-07-30: 스크롤 스토리텔링

### 결정

- 결정: 사용 흐름 밴드와 스크린샷 밴드를 하나의 스티키 장면으로 합친다. 왼쪽 설명 열이 `position: sticky`로 고정되고 오른쪽 스크린샷 열이 단계별로 지나간다.
  이유: 두 섹션이 같은 내용을 텍스트와 이미지로 나눠 설명하고 있었다. 합치면 각 단계의 설명과 화면을 같은 시야에서 볼 수 있고, 스크롤 자체가 설명 순서가 된다.
- 결정: 고정된 열에 진행 표시(`scene-rail`)를 두고 현재 단계를 강조한다.
  이유: 스티키 구간에서는 스크롤해도 왼쪽이 그대로라 진행감이 사라진다. 활성 항목이 바뀌면 어디까지 왔는지 알 수 있다.
- 결정: 진입 애니메이션은 `IntersectionObserver`로 처리하고, 기존 `[data-reveal]` 로직은 건드리지 않는다.
  이유: 홈과 compact 페이지가 기존 로직에 의존한다. 랜딩 전용 속성(`data-rise`, `data-rise-group`)을 따로 두어 서로 간섭하지 않게 했다.
- 결정: 관측이 한 번도 발생하지 않는 경우를 대비해 600ms 후 뷰포트 내 요소를 강제로 표시한다.
  이유: 짧은 뷰포트나 확대 상태에서 콜백이 늦거나 발생하지 않으면 본문이 숨은 채로 남는다. 내용이 안 보이는 것이 애니메이션이 없는 것보다 훨씬 나쁘다.

### 접근성

- `prefers-reduced-motion: reduce`에서는 모든 진입 연출을 끄고 `scene-pin`의 `position: sticky`도 해제해 일반 문서 흐름으로 되돌린다.
- 860px 이하에서는 스티키를 풀고 진행 표시를 숨긴 뒤, 스크린샷과 설명을 세로로 쌓는다. 좁은 화면에서 고정 열은 공간만 차지한다.
- 각 장면의 첫 스크린샷에는 `loading="lazy"`를 두지 않는다. 지연 로딩과 진입 애니메이션이 겹치면 빈 상자가 보인다.

### 검증

- `python3 -m html.parser` 8개 페이지 통과, `git diff --check` 통과, 로컬 HTTP 200 9건(JS 포함).
- Playwright로 데스크톱 1280px에서 스티키 고정과 진행 표시 전환을, 모바일 390px에서 스티키 해제와 세로 적층을 확인했다.
- 주의: `fullPage` 캡처는 스크롤 이벤트가 발생하지 않아 진입 전 요소가 숨은 상태로 찍힌다. 뷰포트 캡처로 확인해야 한다.

## Addendum 2026-07-30: 문체 교정

### 문체 기준 (근거: 커밋 `eb525c1` "Apply updated site copy", 사용자 직접 작성)

사용자가 직접 쓴 문구의 특징:

- 담백한 서술체. `우리 가족의 필요로부터 만듭니다`, `정성껏 만든 앱을 소개합니다`처럼 꾸밈이 적다.
- 문장을 끝까지 맺는다. 명사로 끊거나 체언 종결로 멋을 부리지 않는다.
- `~합니다`, `~하세요`, `~할 수 있습니다`가 기본. 독자에게 권할 때 `~보세요`를 쓴다.
- 자기 미화를 하지 않는다. 앱이 무엇을 하는지 말할 뿐 얼마나 공들였는지 강조하지 않는다.
- 감정을 절제하되 따뜻하다. `당신에게도 기쁨이 되길 바라요` 정도가 가장 감정적인 표현이다.

### 걷어낸 AI 패턴

- 명사 나열 후 마침표: `셔터를 누르는 감각, 사진 아래 남는 기록, 다시 열었을 때 그대로인 설정.` → 서술문으로 풀어 씀.
- 템플릿 대구: `~하는 순간부터 ~하는 순간까지`가 세 페이지에 동일하게 박혀 있었다. 전부 제거.
- 자기 미화: `조용하게 다듬었습니다`, `약속에 집중했습니다`, `그대로 옮겼습니다` → 사실 서술로 교체.
- 과장된 단정: `이런 사람을 위해 만들었습니다` → `이럴 때 쓰면 좋습니다`.
- 번역투 제목: `정확한 조건` → `앱 정보`.
